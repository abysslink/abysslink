<objective>
Extend the daemon to support the approve/deny capability-URL kind and provide the IPC seam for the CLI's gate.Request() blocking call.

This plan adds:
1. Two new content-store kinds (kindApprove, kindDeny) in content.go with prefixed mint functions and updated eviction preference
2. Two new route handlers (handleApprove, handleDeny) on the content mux — bearer-LESS, constant-work, uniform 404, CAS resolve, HMAC verify, audit receipt
3. Two new unix-socket routes (POST /approve/request, GET /approve/wait/{id}) so the CLI can open a pending request and long-poll for resolution
4. approve_pending/approve_approved/approve_denied atomic counters on /status

The approve registry itself lives in internal/approve (Plan 01). This plan imports it. The daemon field approveRegistry is type *approve.Registry, injected via SetApproveRegistry().

Purpose: Close APPR-02 (CAS resolution on the daemon side), APPR-03 (audit receipt), APPR-04 (capability-URL kind + constant-work 404).
Output: Extended daemon with handleApprove/handleDeny, two unix-socket approve IPC routes, /status counters.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| phone→daemon content mux /approve/{token} | Bearer-LESS path: token entropy is the only credential; HMAC is defense-in-depth |
| phone→daemon /deny/{token} | Same trust boundary as approve |
| CLI unix socket→daemon /approve/request | Only reachable from processes with unix socket access (local machine only); no network exposure per WR-04 |
| daemon→audit chain | Audit receipt content is hashed; raw requestID prefix + action string + closureHash are the receipt — never the capability URL |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-30-07 | Spoofing | GET /approve/{token} — capability URL guessing | mitigate | 256-bit token (16 bytes crypto/rand, base64url, ≥128-bit entropy per prefix stripping); brute-force infeasible at standard request rates |
| T-30-08 | Spoofing | Cross-kind probe /approve/{denyToken} | mitigate | lookupKind checks kind BEFORE single-use consume; a deny token presented to handleApprove returns 404 without burning the deny token (BACK-09 invariant applied to kindApprove/kindDeny) |
| T-30-09 | Tampering | Approve-on-timeout / error in daemon handler | mitigate | handleApprove/handleDeny only call Resolve(stateApproved/stateDenied) on a valid lookup hit; error paths return early before Resolve; timeout in handleApproveWait resolves to deny explicitly |
| T-30-10 | Information disclosure | approveURL/denyURL in daemon logs | mitigate | Logs only requestID[:8] and tier; URLs are never written to slog, audit, or any observable surface |
| T-30-11 | Spoofing | HMAC forgery on handleApprove | mitigate | approve.VerifyApproveURL(hmacKey, requestID, "approve", closureHash, storedSig) uses hmac.Equal (constant-time); HMAC mismatch → uniform 404 (same as a token miss — no oracle) |
| T-30-12 | Denial of service | approve-store flooding via repeated POST /approve/request | mitigate | approveTTL is short (120s+30s buffer); content store bound at 512 entries with dropOldestLocked (approve entries are evictable); HMAC key probe disables feature if unavailable |
| T-30-13 | Elevation of privilege | critical-tier action reaching approve capability-URL path | mitigate | handleApproveRequest rejects critical tier with 403 before minting any token; critical path is TTY-only (D-07) |
| T-30-SC | Tampering | npm/pip/cargo installs | accept | No new external packages — internal/approve (Plan 01 local package); already-in-go.mod deps only |
</threat_model>
