#### T-002 — [CRITICAL/LOG] `internal/ui/theme.go:47` (color-contrast)

- **Problem:** The four semantic colors that drive virtually all status/health output are flat lipgloss.Color values, NOT lipgloss.AdaptiveColor: ColorSuccess #04B575, ColorWarn #FFD060, ColorFatal #FF5F87, ColorInfo #5C7CFA. Unlike the brand palette directly above (ColorAccent/ColorSelection/ColorMuted at lines 30-38, which ARE AdaptiveColor with light-mode counterparts), these never adapt to a light terminal. Measured WCAG contrast on a white terminal background: ColorWarn yellow = 1.45:1, ColorSuccess green = 2.67:1, ColorFatal red = 2.90:1, ColorInfo blue = 3.67:1 — all fail WCAG AA (4.5:1), and yellow is effectively invisible. These styles flow into styleWarn/styleSuccess/styleFatal/styleInfo (styles.go:42-48), the status icons (iconWarnStr/iconOKStr/iconFatalStr), the doctor WARN/FATAL labels (cmd_doctor.go:617,627,737,741), the status panel rows (cmd_status.go:514-517), and the livetable (tui.tuiWarn/tuiSuccess). lipgloss does NOT auto-adjust a flat hex for terminal background; only AdaptiveColor switches on the detected light/dark profile.
- **Impact:** A user on a light-background terminal (very common: default macOS Terminal/iTerm light themes, many SSH clients on phones with a light scheme) sees the WARN icon and the entire 'WARN' label as near-invisible pale yellow on white — they can miss security warnings entirely in `abysslink doctor`. Green OK and red FATAL are also below readable contrast, washing out the at-a-glance health status the status/doctor screens are built around.
- **Before (rendered):** abysslink doctor on a white-background terminal: the per-finding lines show a barely-perceptible pale-yellow triangle and a ghost-grey-yellow 'WARN' word that blends into the page; the green check icons look like faint mint smudges; only the bold finding name (no color) is clearly legible. The final 'N warn' counter line is similarly washed out.
- **Fix:** Promote the semantic palette to AdaptiveColor with darkened light-mode counterparts, exactly as the brand palette already does (theme.go:30). e.g. ColorWarn = AdaptiveColor{Dark: "#FFD060", Light: "#946200"}, ColorSuccess = {Dark:"#04B575", Light:"#02764C"}, ColorFatal = {Dark:"#FF5F87", Light:"#B3003A"}, ColorInfo = {Dark:"#5C7CFA", Light:"#2540C0"}, each chosen to clear 4.5:1 on white. Note the byte-stability comment at theme.go:42-44 claims these must stay flat for --json/non-TTY byte stability, but those surfaces already strip ANSI (printer.go:103) or disable color, so AdaptiveColor renders identically (no ANSI) there — re-baseline the golden fixtures in internal/cli/testdata and internal/tui/testdata after the change. Icon+word labels already partially mitigate per §10, but the colored text itself must still be legible.
- **Confidence:** high  ·  verify 2/2

#### T-001 — [HIGH/AUTO_FIXABLE] `internal/tui/notes.go:74` (layout)

- **Problem:** noteBoxStyle computes width as `w := terminalWidth()-4; if w < 54 { w = 54 }` — i.e. it FLOORS the box width at 54 columns. The identical anti-pattern is in secret.go:73-78 (secretBoxWidth) and header.go:57-61 (JourneyHeader). This directly contradicts internal/cli/styles.go:59-64 boxWidth(), which deliberately CAPS at min(54, termwidth-2) with an explicit comment: 'The marketed environment is a phone SSH client that is frequently narrower than 54 columns; a fixed width there makes lipgloss hard-wrap the borders into garbage (UX review #10/#6).' So the cli boxes are phone-safe but the tui boxes (Note/SecretBox/JourneyHeader) are not — on any terminal narrower than 54 columns they are pinned to 54 and overflow the viewport.
- **Impact:** On a sub-54-column phone terminal, every security callout box and (critically) the once-only Tailnet Lock disablement-secret box renders wider than the screen. The terminal soft-wraps the over-wide border rows, splitting the rounded box border across lines into broken '|' / '─' fragments. For SecretBox specifically this can make the disablement secrets — shown exactly once and never recoverable — hard to read/copy on the very device the product targets.
- **Before (rendered):** On a ~40-column phone terminal: a red-bordered box whose top border line wraps onto a second line, so the box appears to have a stray border fragment hanging below it; secret lines run past the right edge and wrap, misaligning with the left border column. The box no longer reads as a clean rectangle.
- **Fix:** Replace the `if w < 54 { w = 54 }` floor with the same cap logic as cli boxWidth(): clamp to the terminal width (e.g. `w := terminalWidth()-4; if w > defaultWidth { w = defaultWidth }` and additionally allow it to shrink below 54 when the terminal is narrower). Best: have internal/cli pass the already-correct boxWidth() into these tui renderers as a parameter (mirroring the BannerOptions.Width pattern in ui.RenderBanner) so there is a single width source of truth and the leaf tui package stops re-deriving an incompatible one.
- **Fix steps:** In internal/tui/notes.go noteBoxStyle (line 74-78) replace the floor with a cap matching cli.boxWidth(): `w := terminalWidth() - 4; if w > 54 { w = 54 }` so it shrinks below 54 on narrow phone terminals instead of pinning to 54. Re-run/re-bless any tui golden fixtures in internal/tui/testdata, then `make lint test`.

#### T-023 — [MEDIUM/AUTO_FIXABLE] `internal/tui/spinner.go:80` (keyboard-nav)

- **Problem:** The three interactive surfaces respond to the Esc key three different ways. LiveTable treats Esc (and Ctrl-D) as a quit synonym for Ctrl-C (livetable.go:157-159: case tea.KeyCtrlC, tea.KeyCtrlD, tea.KeyEsc → tea.Quit). The spinner does NOT — its Update only matches tea.KeyCtrlC (spinner.go:83-85) and drops Esc/Ctrl-D via the default `return m, nil`. The huh wizard forms abort on Ctrl-C only and ignore Esc entirely (huh form.go:558, Quit=ctrl+c). So the same Esc keystroke aborts the scan/apply progress table, but is a silent no-op during a spinner and during every wizard prompt.
- **Impact:** A user who learns during `abysslink up` that Esc cancels the live module table will press Esc during a spinner (e.g. a background converge step) or during the init wizard and find it does nothing — they must rediscover Ctrl-C. Inconsistent cancel keys across screens of the same binary is a classic keyboard-nav defect; the user cannot build a reliable muscle-memory for "get me out of here".
- **Before (rendered):** Two near-identical single-line spinner rows: one is the LiveTable in-flight row ("◌  scanning...") which vanishes the instant Esc is pressed; the other is the standalone spinnerModel ("◌  <label>") which keeps animating unchanged when Esc is pressed — only Ctrl-C stops it. Visually indistinguishable, behaviorally divergent.
- **Fix:** Make the cancel keys consistent. In spinner.go Update, accept tea.KeyEsc (and optionally tea.KeyCtrlD) as quit synonyms exactly as LiveTable does, so Esc cancels any animated indeterminate work. Note the spinner is wired with tea.WithContext so quitting only stops the visual; that is acceptable and matches the documented WR-02 contract — the consistency fix is about which keys trigger the quit, not about side-effect cancellation.
- **Fix steps:** In internal/tui/spinner.go Update (case tea.KeyMsg, lines 80-86) change `if msg.Type == tea.KeyCtrlC` to `switch msg.Type { case tea.KeyCtrlC, tea.KeyCtrlD, tea.KeyEsc: return m, tea.Quit }` (then `return m, nil`), mirroring livetable.go:157-161. Add/extend a spinner_test.go case asserting Esc and Ctrl-D return tea.Quit. Run `make lint test`.
- **Confidence:** high  ·  verify None/0

#### T-018 — [MEDIUM/LOG] `internal/tui/styles.go:24` (color-contrast)

- **Problem:** tui.noColor() only checks the NO_COLOR env var, whereas the CLI's colorEnabled() (term.go:45-53) also disables color for CLICOLOR=0 and, crucially, for non-TTY output (pipes, files, CI, redirected logs). - **Impact:** When a user pipes `abysslink ...` output into a file, a pager, or a CI log on a system without NO_COLOR set, Note/Security/Danger callouts and the journey header render with their colored unicode glyphs (●/⚠/✕) and rounded borders rather than the clean ASCII (*/!/x, +/-/|) fallback, producing harder-to-read or mojibake-prone captures — the same readability regression the ASCII fallback was designed to prevent.
- **Before (rendered):** abysslink output redirected to a log file then viewed in a plain pager: a security Note box still shows a rounded-corner border and a colored '● SECURITY' label (with escape residue in non-ANSI viewers) instead of the intended '+----+' ASCII box and '* SECURITY' plain label.
- **Fix:** Give internal/tui a capability input that mirrors colorEnabled() rather than a bare NO_COLOR check. Per the IO-boundary pattern already used for banner (BannerOptions carries Color computed by the caller, banner.go:37-41), thread a color/no-color boolean into Note/SecretBox/JourneyHeader from internal/cli (which computes colorEnabled()), or at minimum extend tui.noColor() to also return true when stdout is not a TTY and when CLICOLOR=0, matching term.go.
